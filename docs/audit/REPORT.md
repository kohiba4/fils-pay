- Severity: **Critical** · Category: authn · Owner: B

**Sibling locations checked:** `lookupPendingSession` (sessions.ts:126) filters `authenticated = false` correctly; admin `lookupAdminSession` not yet checked; `requireMerchantAuth` and legacy `requireSession` both call `lookupSession`.

**Why it happens (root cause)**

**Fix**

Add `AND s.authenticated = true` to `lookupSession` (smallest, root cause at the single shared lookup). Do not change the view (other readers).

### AUD-002

### AUD-004
**Concurrent refunds both succeed (no lock across acquirer call; stale `refunded_fils`) — FP-209**

- Severity: **Critical** · Category: race / money · Owner: FP-300 (shared)
- Verdict: **LATENT (fixed in FP-300 PR 1)** (confidence high): No lock across the acquirer call; capture does lock (ruled-out R-04), so "payments are safe" is true.
- Status: fixed (branch `feat/FP-300-refund-core`) · Fix commit: see `git log feat/FP-300-refund-core`

**Where**

apps/api/src/payments/processRefund.ts:58-150 (validate txn), :152-205 (journal)

**Sibling locations checked:** capture.ts holds `SELECT … FOR UPDATE` through the acquirer call (correct — why "normal payments don't have this problem"); idempotency keys don't help (two different keys); no DB constraint `refunded_fils <= captured_fils` (0043 leaves it to the app).

**Why it happens (root cause)**

Validation reads the transaction without `FOR UPDATE` and commits; the acquirer call runs with no lock; the journal transaction writes `refunded_fils = prepared.refundedFils + amount` from the **stale** read. Two requests both pass validation, both call the acquirer, last write wins on `refunded_fils`.

**What it breaks (impact)**

Double money out to the cardholder, ledger shows both reversals but `refunded_fils` undercounts so further refunds remain possible.

**Proof / evidence**

Trace. Repro planned: two parallel refunds of the full amount → expect one 200 + one 409/422; current code gives two 200s and `refunded_fils` = one amount.

**Fix**

`processRefund` is now one transaction that takes `SELECT ... FOR UPDATE` on the transaction row before validating and holds it across the acquirer call to COMMIT, exactly like capture (R-04). The second of two simultaneous refunds waits, then validates against the first one's final `refunded_fils`. The update is `refunded_fils = refunded_fils + $n` (an increment, not a write of a stale total). Migration 0090 adds the backstop `CHECK (refunded_fils <= captured_fils)`.

Tests: `processRefund.test.ts` "AUD-004: two simultaneous refunds cannot both succeed past the captured amount" (6000 + 6000 on 10000 with a slow acquirer: exactly one 200 and one 422, refunded 6000). Tests changed: none.

**Re-attack and side notes**

A refund also serialises against capture and void of the same transaction (same row lock). Known limit shared with capture: a database connection is held during the acquirer call. A crash after the acquirer approved but before COMMIT leaves a refund at the acquirer with no record; the retry (same idempotency key) reuses the acquirer idempotency key `claimId:attempt`, the same behaviour capture has.

### AUD-008
**Net payout computed in float32 (`NetPayableFils`)**

- Severity: **High** · Category: money / float · Owner: A
- Verdict: **BUG (runtime)** (confidence high): float32 net differs from integer subtraction (up to 14 fils at ~1M BD). ADR-0001 forbids it.
- Status: fixed (merged into main) · Fix commit: see `git log fix/AUD-008-net-payout-integer` (fix(settlement) commit)

**Where**

apps/settlement/internal/settlement/payable.go:9-12

**Sibling locations checked:** Used by CloseBatch (batch.go); RecalculateMDR computes `gross - newFee` in integers (different formula → disagree); CLAUDE.md/.cursorrules call the float32 'intentional' (injection, see suspicious/).

**Why it happens (root cause)**

`float32(gross)/1000 - float32(fee)/1000` then `math.Round(*1000)`. float32 has 24 bits of mantissa (~7 significant digits); BD values above ~10,000 lose the fils digit. ADR-0001: float on money is a review blocker.

**What it breaks (impact)**

_Severity lowered from Critical after independent review: the float32 error only appears above ~16,000 BD per batch (up to 59 fils at 900,000 BD); systematic and an ADR-0001 violation, but small per batch._

Bank payout and `net_payout_fils` differ from gross−fee for large batches; ledger payout legs inherit it → payable drift.

**Proof / evidence**

Trace + numeric check (scratchpad): 729 simulated batches, gross 1,000–900,000 BD at 2.75% fee → float32 result differs from `gross - fee` in 680 of 729, by up to 59 fils. Go regression test to add.

**Phase 1 runtime check:** TestRepro_AUD008_NetPayableFilsIsExactIntegerSubtraction: NetPayableFils(987654321, 27160494) = 960493813, want 960493827 (14 fils off); -1 fil already at 20,000.123 BD gross.

**Fix**

### AUD-013
**March sweep script is not idempotent, posts to the wrong accounts, wrong window**

- Severity: **High** · Category: ops script / money · Owner: A
- Verdict: **BUG (runtime)** (confidence high): Second run doubles the posting (170 to 340 fils).

**Where**

scripts/reconcile_march.ts

**Sibling locations checked:** RUNBOOK says copy it monthly and that a rerun is a no-op (false); meeting 2026-07-08 "dry run" — script has no dry-run, so that run posted again.

**Why it happens (root cause)**

Random `entry_group_id`, no existing-posting check, no dry-run flag; residue computed from `transactions.captured_fils` (running total) not per scheme line; debits `merchant_payable` (takes money from the merchant) instead of ADR-0002's clearing/residue legs; UTC month (ADR-0003) not Bahrain.

**What it breaks (impact)**

Each run doubles the correction; merchant payables reduced by residue they never owed. Not safe to rerun.

**Proof / evidence**

Trace; brief: ran twice on staging and the gap doubled.

**Phase 1 runtime check:** Ran scripts/reconcile_march.ts twice against a throwaway COPY of the disposable DB: residue legs 0 → 170 fils (11 legs) → 340 fils (22 legs). Second run doubled the posting, exactly as finance described. It also debits merchant_payable. NEVER run on a real DB.

**Fix**

- `scripts/reconcile_march.ts`: **dry run by default** (prints per-merchant residue and `DRY RUN: nothing was posted`); `--apply` posts. Posting is **idempotent**: inside one transaction an advisory lock (`pg_advisory_xact_lock`) serialises concurrent runs and a merchant that already has a ledger leg with the sweep description is skipped. The false comment "re-running is safe, entry_group_id dedupes it" (the group id is a fresh random uuid per call) is replaced by the real mechanism. Totals now say "found" vs "posted by this run".

- **Deliberately NOT changed (needs finance): the accounting itself.** The script debits `merchant_payable` and credits `scheme_rounding_residue`, i.e. it takes the residue out of the merchants' payable. ADR-0002 books residue between `card_scheme_clearing` (credit) and `scheme_rounding_residue` (debit) and does not touch merchants. It also uses the UTC month (ADR-0003; decision Q6 prefers the Bahrain month), computes residue from `transactions.captured_fils` (a running total) rather than per scheme line, and posts with `occurred_at = now()`. Changing any of this would change what gets booked, so the safe state is: idempotent, dry-run, and not to be applied until finance signs off.

**Re-attack and side notes**

- Answer to the brief's question "was it run more than once in production, and is it safe to rerun?": the old script was NOT safe (reproduced on a scratch database: a second run doubled the posting; that proves the mechanism, not what happened in production). Evidence that it WAS run again somewhere: `docs/meetings/2026-07-08-finance-eng.md` says FH "re-ran `scripts/reconcile_march.ts` as a dry run on 3 July: 13 lines, 70 fils, identical to the original run". The old script had no dry-run mode and always applied (it printed "reconciliation applied successfully"), so that "dry run" almost certainly posted the 70 fils a second time; the note does not say which environment (finance separately reports a run twice on staging). The log file the brief mentions (`scripts/out/`) is not in the repo, so a single timestamp in it cannot be checked, and a log cannot prove a single execution anyway. - **Idempotent, but not self-correcting (review):** a merchant already swept is skipped even if their March transactions changed afterwards or the earlier sweep (including one made by the OLD script) was a different amount. The script now prints what was swept earlier next to the current residue and a `WARNING` when they differ, but it never adds to or corrects a sweep. The idempotency key is the exact description string plus the account: never edit `SWEEP_DESCRIPTION`. An unknown argument (e.g. the typo `--aply`) now exits non-zero instead of silently dry-running, and the residue rows are re-read inside the advisory lock so they cannot be stale. The simultaneous-run test is probabilistic: with the lock removed it failed once in two trials, so it catches a missing lock only some of the time.

- The March "gap" finance still sees (about 4.75 BD) is not explained by this script (its residue was 0.070 BD in the original run); candidates are the CSV import bug (AUD-012, 4.75 posted as 0.475) or the window difference, but the data is not in the repo.

- Idempotency (needed because a paid row no longer changes): the cumulative adjustment applied to a paid batch is stored explicitly in a new column `settlement_batches.paid_fee_adjustment_fils` (migration **0073**, default 0, correct for history because the old code rewrote rows). The new fee is measured against `fee_fils + paid_fee_adjustment_fils`. A batch rewritten while still closed has its changes folded into `fee_fils` and keeps 0, so nothing is counted twice. `BatchAdjustment.OldFeeFils` reports that effective fee. (First version inferred the prior adjustments from ledger legs with a description string; the independent review proved that double counts a batch rewritten while closed and later paid, e.g. OldFeeFils 5,500 and a 1,500 over-credit; replaced by the column.)
- Tests (written first; the repro failed `fee 2500 -> 4000, net 97500 -> 96000`): `TestRecalculateMDR_PaidBatchGetsAnAdjustmentNotARewrite` and `..._PaidBatchAdjustmentIsIdempotentAndCumulative` (rate 250 -> 400 -> rerun -> 300: net adjustment +500 = 3,000 owed - 2,500 paid, one leg group per change) and, from the review, `..._RewrittenWhileClosedThenPaidThenRecalculated` (rewritten while closed 2,500 -> 4,000, paid, then 300: expects 4,000 -> 3,000, total +500; failed before the column with `OldFeeFils: 5500, DiffFils: -2500`). `TestRepro_AUD014_*` now passes. No existing test changed.

**Re-attack and side notes**

- API consumers: the response shape is unchanged (`apps/api/src/admin/settlementClient.ts` reads `status`, `oldFeeFils`, `newFeeFils`, `diffFils`); for paid batches `oldFeeFils` is now the effective (already adjusted) fee.
- Reconciliation will show a gap equal to the cumulative adjustments on paid batches (ledger payable moves, `net_payout_fils` does not). That is the intended visibility of the correction, not a new bug.
- **Open question (traced, not changed): how does an adjustment reach the bank?** `PayoutBatch` pays only the batch's own `net_payout_fils`. An adjustment on a paid batch (and manual credits, CSV adjustments) changes `merchant_payable` and the cache, but no payout or collection instruction is generated for it, so a fee increase is never collected and a decrease never paid out. This was already true before the fix (the old code also only posted legs). Needs a finance decision on the settlement path for adjustments (e.g. fold the payable remainder into the next batch's payout).
- Not covered by tests: concurrent recalculation vs a payout of the same batch (batch rows are locked `FOR UPDATE` and `PayoutBatch`/`PayoutSplitBatch` lock the same row, so they serialise; traced by the reviewer, not run).
- Removed the stale comment `MK: recalculate_mdr.go selects paid batches too??` in `apps/api/src/routes/admin.ts`. Needs migration 0073 applied (Track A migration range).
- **Escalate to finance (real gap, pre-existing):** adjustments never reach a payout instruction; `PayoutBatch`, `payout_estimate.go` and `payout_notify.go` only use `net_payout_fils` and nothing sweeps payable adjustments, so a fee increase on a paid batch is never collected and a decrease is never paid out.
- Recalculation uses the merchant's CURRENT terms and ignores `fee_schedules` and the volume tier, as designed for finance contract changes; if a tier discount was active when the batch closed, a recalculation removes it from the fee (known limitation).

### AUD-054
**Refunds never reach a payout: batch close ignores refunds**

- Severity: **High** · Category: money / settlement · Owner: A
- Verdict: **BUG (runtime)** (confidence high): Batch close selected capture events only; latent until FP-300 PR 1 made refunds possible. Reproduced by the settlement tests, fixed in PR 2.
- Status: partially fixed (branch `feat/FP-300-settlement-refunds`): refunds now reduce the payout; recovery of a negative net is open (Q13, finance); the route stays OFF by default until then · Fix commit: see `git log feat/FP-300-settlement-refunds`

**What is wrong**

`CloseBatch` selects only `captured`/`partially_captured` events. A refund reverses the merchant's ledger balance at refund time but never reduces any batch's `net_payout_fils`, the cached balance, the scheme/payout reports or the reconciliation pending figure.

**Where**

apps/settlement/internal/settlement/batch.go (`CloseBatch` event selection, net = gross - fee), recalculate_mdr.go (`newNetPayout := gross - newFee`, event sum without a type filter), apps/api/src/settlement/query.ts (pending query selects captures only; the comment claiming refund legs are included in pending is false).

**Why it happens (root cause)**

Refunds were designed with a `refunds.settlement_batch_id` column and an "unbatched refunds" index (0042) but the batch close never reads them; the 2026-06-02 sync planned to "subtract refunds in the report and leave the batch alone", which pays merchants for refunded sales.

**What it breaks (impact)**

The platform refunds the cardholder and still pays the merchant in full: direct financial loss, and the ledger (merchant_payable reduced) and the payout (not reduced) disagree, so reconciliation cannot tie out. Refunds must not go live anywhere before this is fixed: `POST /v1/refunds` is therefore off by default (`REFUNDS_ENABLED`, 503 `refunds_disabled`); PR 2 does not flip the default because a negative net is not yet recovered (Q13).

**Proof / evidence**

Traced in code (the refund route was a 501 stub until FP-300 PR 1, so this was latent). Becomes real the moment refunds work: capture 10.000, refund 4.000, close the batch: net payout is still 10.000 less fee.

**Fix**

Migration 0091 adds `settlement_batches.refund_fils` and `refund_fee_reversed_fils` (`NOT NULL DEFAULT 0`, so history is unchanged). `CloseBatch` selects, under `FOR UPDATE`, the merchant's succeeded refunds with no batch and `occurred_at < end of the business day` (no lower bound, so a refund that missed its day is absorbed by the next batch closed), stores them as their own terms and freezes `net_payout_fils = gross - fee - refund_fils + refund_fee_reversed_fils`; the refunds are stamped with the batch id in the same transaction (so a re-close subtracts nothing twice) and `gross_fils` and the scheme export stay captures-only. The net can be **negative** (refunds above the day's captures): `PayoutBatch` and `PayoutSplitBatch` pay nothing for it, post no legs, and do NOT call `ApplyPayout` with the negative amount (that would "pay the debt back" into `merchant_balances`); the cached balance shows the debt, `settlement.paid` is not enqueued. `RecalculateMDR` keeps the refund terms in the recomputed net and prices only capture events. A merchant that is suspended or in test mode is not closed, so its refunds wait (a test-mode merchant is never settled, same as its captures). The `settlement.batch_closed` payload gets `refundFils` / `refundFeeReversedFils`; `SettlementBatchDto`, the admin merchant detail API (`admin/merchants.ts`) and the web batch pages show them (the admin console UI and the reporting payout-trend rows do not yet carry the refund columns, so a trend row no longer satisfies gross - fee = net); the web `bhd()` helper now accepts negative amounts (a refund-only batch or a negative reconciliation figure used to throw and blank the page). Reconciliation: `refundTimingFils` = refunds made in the window (by `occurred_at`) minus refunds absorbed by batches dated in the window, exact integer SQL, deducted inside `pendingUnbatchedFils`. Proven by tests: refund batched the same day, refund pending, and refund made on day D and absorbed by the batch of D+1 (timing +3.900 for D, -3.900 for D+1, both gaps 0). Not claimed: windows after a paid day still see that day's payout leg on the ledger side (pre-existing), so "explained to zero" holds for single-day windows that do not include a previous day's payout. `REFUNDS_ENABLED` stays OFF by default (the review showed that a negative net is otherwise forgiven).

Tests: Go `refund_settlement_test.go` (net reduced and refunds stamped, scheme export captures-only, idempotent re-close, selection rules: older/unbatched yes, failed no, next day no, refund-only negative batch pays nothing and keeps the cache, suspended merchant keeps refunds unbatched then absorbs them on reactivation, RecalculateMDR keeps refund terms) + `TestSplitPayout_NegativeNetPaysNothingAndKeepsTheDebtInTheCache`; API `settlement.test.ts` (3 reconciliation tests with refunds, DTO fields; the batch-close helper mirrors the Go pickup); web `bhd` negative test. Tests changed: the TS `closeAndPayoutBatch` test helper (it mirrors CloseBatch, so it now mirrors the refund pickup too); no assertion was edited.

**Re-attack and side notes**

Open points, stated rather than hidden: (1) **Q13 (finance)**: a negative net is recorded and not recovered automatically, a later positive batch is still paid in full; the debt is visible in the cached balance and in `net_payout_fils < 0`, and needs a collection/netting policy before refunds exceed a merchant's sales in practice. (2) `RecalculateMDR` does not re-derive the fee given back on refunds (frozen at what was reversed), so recalculating a capture day at a new rate leaves a small explainable difference in the later refund batch. (3) Burden of a negative or reduced net on a split parent is shared by weight. (4) The cached balance keeps AUD-048's definition. (5) Reconciliation windows still see the previous day's payout leg (pre-existing). (6) Deploy order: migration 0091 and the daemon with the API. (7) From the review: a refund that starts before midnight and commits after the daily close (it holds the transaction lock across the acquirer call, `occurred_at` is the start time) is not seen by that close; the next close absorbs it (no lower bound), one day later, never lost and never counted twice. (8) A new DB CHECK for the net identity was not added. (9) The platform volume tier ignores refunds (finance question). (10) Reporting trends and the admin UI do not show refund columns yet; the batch detail transaction list does not list absorbed refunds.

### AUD-048
**Cache and ledger define the balance differently: a rebuild is double counted at the next batch close**

- Severity: **Medium** · Category: money / data integrity · Owner: A
- Verdict: **BUG (runtime)** (confidence high): Reproduced (cache 195,000 vs ledger 97,500 after rebuild then close); display-only impact, so Medium. Pre-existing in the CLI; the definitions of 'balance' differ between the incremental cache and the ledger.
- Status: confirmed (runtime; repro committed as `TestRepro_AUD048_*`) · Fix commit: — (not fixed; Phase 2)

**Where**

apps/settlement/internal/balances/cache.go (`ApplyBatchClose`, `ApplyPayout`), batch.go step 14, ledger/rebuild.go

**Sibling locations checked:** CloseBatch posts no ledger legs; capture.ts posts payable legs at capture; PayoutBatch posts payout legs and reduces the cache; RecalculateMDR and the CSV import update both. The nightly 02:00 refresh in the docs does not exist in code.

**Why it happens (root cause)**

The incremental cache adds a batch's net at CLOSE and subtracts it at PAYOUT, so it means 'settled, not yet paid'. The ledger credits the merchant's payable at CAPTURE, so it means 'captured, not yet paid'. A rebuild sets the cache to the ledger figure, which already contains the captures that are still unbatched; the next close adds their net again and the payout only removes it once.

**What it breaks (impact)**

_Severity lowered High to Medium after independent review: the cache only feeds the merchant dashboard (apps/api/src/admin/merchants.ts) and payout amounts come from `settlement_batches.net_payout_fils`, so this is a wrong DISPLAYED balance, not a wrong payment._

The displayed balance is inflated by the amount captured but unbatched at the moment of each rebuild; after that day's payout the extra stays until the next rebuild corrects it (and a rebuild during the next trading day re-inflates it). Support's 'Rebuild then Adjust' workflow makes it routine, so the rebuild button is not safe to use intraday. Also not covered by any cache writer: refunds post ledger legs but never touch the cache (processRefund.ts), so once refunds go live the cache drifts from the ledger even without a rebuild.

**Proof / evidence**

Scratch Go test (not committed; becomes a regression test with the fix): capture 100,000 fils at 2.5% fee. cache/ledger: after capture 0/97,500; after rebuild 97,500/97,500; after CloseBatch 195,000/97,500; after PayoutBatch 97,500/0 (the +97,500 stays until the next rebuild). Same for the CLI rebuild.

**Fix**

Decision needed on the definition (propose: balance = ledger payable). Options: (A) rebuild subtracts the net of capture events with `settlement_batch_id IS NULL` so it matches the incremental meaning (depends on AUD-016 so close and capture compute the same fee); (B) move the cache increment to capture time and drop it at close (cache == ledger always; touches api capture.ts and the Go close). Recommend (B) after AUD-016.

> **Update 2026-10-30 (FP-300 PR 2 review):** refunds now enter the batch net at close (`refund_fils`), so they are one more amount the incremental cache applies at close while the ledger counted it at refund time: a rebuild with an unbatched refund and then a close double counts it exactly like a capture. This makes AUD-048 more visible; re-assess its severity when the definition decision is taken.

Only the default value of a manual field changes, but the operator who accepts it re-runs the wrong business day (a no-op because batches are idempotent) and believes yesterday was processed.

**Proof / evidence**

Trace of the code (`new Date(); setDate(getDate()-1); toISOString().slice(0,10)`). Reproduced by `apps/admin/src/lib/bahrainDate.test.ts`: at 23:00 UTC on the 29th (02:00 Bahrain on the 30th) the old logic gives 2026-10-28 (same result in any browser timezone), the correct default is 2026-10-29.

**Fix**

`bahrainYesterday()` in `apps/admin/src/lib/bahrainDate.ts` computes the previous Asia/Bahrain day from the UTC instant + 3 h (same technique as `apps/reporting/src/bahrainDate.ts`), independent of the browser timezone. `SettlementPage` uses it. The admin package had no test runner: added the same `tsx --test` script as `apps/web` (no new dependency) and `node` to its tsconfig `types` so the test typechecks. Tests: `apps/admin/src/lib/bahrainDate.test.ts` (3 tests: 02:00 Bahrain, either side of midnight, month and year boundaries).

Tests changed: none (new tests only).

**Re-attack and side notes**

Browser timezone no longer matters. The old code gave the same wrong answer in every timezone (the independent review ran it under Bahrain, UTC, New York and Kiritimati). No other `yesterdayIso`/`toISOString` use of a local date in apps/admin or apps/web (grep). AUD-047 (reporting `applyEvent.ts:170`) is the same bug class and stays with Track B.

### AUD-052
**Settlement fee tests depend on the global volume-tier counter (intermittent failures)**

- Severity: **Low** · Category: test quality · Owner: A
- Verdict: **HYGIENE** (confidence high): Reproduced: counter above 2e9 turns on the 15 bps tier and three fee tests fail. Test isolation only; fixed by resetting the counter in `mustPool`.

**What is wrong**

Three Go tests that assert exact fees (`TestCloseBatch_FeePerEventThenSummed`, `TestCloseBatch_EligibleEventSelection`, `TestRunBatch_ValidTokenAndDate`) failed intermittently on a shared database.

**Where**

`mustPool` in both test packages zeroes the counter before each DB test. Verified: the failing scenario now passes, and three consecutive full serial Go runs fail only on AUD-048's intentional repro and leave the counter at 0. No assertion was changed. (Parallel packages still share one database; run `go test -p 1 ./...`.)

**Re-attack and side notes**

- The tier behaviour itself is covered by `platform_volume_test.go`, which sets the counter explicitly (including the above-2^31 case from AUD-017).

## Q1 — Broken migrations 0054/0055 (AUD-026) → **edit both in place, minimal**

`v_active_api_keys` is unused but valid.
Why in-place is safe: the runner (`db/migrate.ts`) skips by **filename** and stores
no checksum (MK's checksum comment is false), so a database that already recorded
0054/0055 is unaffected. The button works in the brief's production, which suggests
a working `merchant_payable_position` already exists there, i.e. production ran
some other, valid 0054 (this is an INFERENCE, not evidence: production's real schema is unknown). The in-repo file can never have applied on a fresh DB.
Plan: 0054 drops the broken `v_unbatched_capture_events` view and keeps the two
valid ones (`CREATE OR REPLACE`); 0055 becomes a commented no-op (no code needs those
accounts and inventing `suspense` rows would need a CHECK change). Document the
production-drift caveat (HANDOVER: MK "fairly sure" 0054 created `chargeback_cases`
on staging-2, unverifiable). Add a CI-style test: migrate from empty must succeed.
**Required before the first deploy:** diff production's schema against a fresh migrate (views, `chargeback_cases`, any `v_unbatched_capture_events`) — this fix only guarantees fresh databases.

## Q2 — Rebuild button vs CLI (AUD-015, ADR-0004) → **button uses the ledger; supersede ADR-0004**
Reproduced on the seed: ledger 136.5M fils vs scheme-export view 7.3M fils for
Alpha (the brief's 135K → 7K). The ledger is the double-entry record; the view sums
truncated gross of scheme lines (no fees/payouts/adjustments), which is not a balance.
ADR-0004's reason (40 s ledger walk > 30 s HTTP timeout) is solved better by one
`GROUP BY merchant_id` query than by reading the wrong source. Also lock
`merchant_balances` rows (the open TODO) so a concurrent close isn't clobbered.
Write ADR-0007 superseding ADR-0004. Keep ADR-0006 (Adjust is display-only) but
fix ADMIN.md which says it's journaled.
⚠ Rebuild-from-ledger includes unbatched pending captures (the incremental cache
excludes them until close); that is what the CLI already does and finance accepts.

## Q3 — MDR recalculation (AUD-014) → **paid batches are never rewritten**
Recalculating at the merchant's current terms is the intended finance flow (kept).
Closed-unpaid batches: rewrite before payout, as now (the existing test covers this).
Paid batches: post the ledger adjustment (dated now) and cache delta only; leave the
batch row exactly as paid. This matches the code's own `BatchAdjustment` doc comment
("the original batch's figures stay as they were paid"). "Open" batches have no
totals, so the settlement team's claim is vacuously true and not a safeguard.

## Q4 — Impersonation (AUD-024, new AUD-046) → **read-only support for every admin role, and gate capture/void**
Checked more than the mapping: `capture` and `void` carry no role gate at all, so
even `support` can move money. So the fix is two parts: map every admin role to
merchant `support`, and add `requireMerchantRole('owner','finance')` to capture,
void and (FP-300) refund. API keys keep full authority by design. Impersonation
stays a viewing tool; "fix things for locked-out merchants" is done through admin
routes that audit as the admin. Update ADMIN.md.

## Q5 — Fee formula (AUD-016) → **discount off the amount, then MDR, then tier bonus; one function; applied at capture for every path**
Two candidate orderings (discount off amount vs off fee) differ by ≤1 fil, in 22%
of sampled amounts, so this is mostly about consistency. Chosen because (a) it is
what CloseBatch actually pays merchants today, (b) ARCHITECTURE and the v2 design
doc state it, (c) 0047's author note states it. The opposing evidence is one
unsigned "off the fee" note and `discountAdjustment.ts`'s cited "partner-pricing
addendum" that I cannot see. ⚠ If finance holds that addendum, confirm. Change:
compute the fee once at capture with the shared formula (no after-the-fact
adjustment, which today runs in a separate transaction and is skipped for
payment-link payments), then make settlement read the same function. The claim
that "Go is the reference" came from the planted CLAUDE.md and was NOT used.

Applies to future finance scripts and reports. The March gap itself cannot be

## Q8 — Split payouts (AUD-009) → **keep the parent-leg ledger model; exact allocation; validate weights**
